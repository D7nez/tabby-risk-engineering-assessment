The workflow uses data-driven testing. Excel supplies the authored expectations, JSON carries those values to the runner, and the runner compares them with both local implementations.

| Worksheet | What to review |
|---|---|
| Design Guide | Rule interpretation, why the scenarios were selected, and open contract assumptions |
| Decision Table | All nine rule-state combinations with expected outputs and supporting case IDs |
| Open Questions | Contract questions, current assumptions, and affected cases |
| Boundary Walkthrough | An Excel formula checks the exposure gate below, at, and above 120% of the credit limit |
| Test Cases | 88 synthetic cases with full inputs, authored expected outputs, and the rationale for each case |

[Methodology](METHODOLOGY.md) includes the decision table, baseline inputs, and specification questions. For a concrete example, find **R2-016** in both workbooks. An exposure of 11,000 sits between the base limit of 10,000 and the policy threshold of 12,000. The expected outcome catches an implementation that uses 100% instead of 120%.

## Reproduce the assessment

Install the dependencies with Python 3.10 or newer and run the workflow from this directory.

```text
python -m pip install -r requirements.txt
python run_assessment.py
python -m unittest discover -s tests -v
```

On Windows, use `py` if needed. To add a case, enter a new row on **Test Cases**, assign a unique ID, and record the expected decision and stop factors from the specification before running the checks. Write the authored inputs and expectations as cell values. Keep payment_is_test as text and phone_verified as a Boolean. Exploratory rows retain TBD expectations and are exported for traceability. Save the workbook and close any generated report open in Excel before rerunning.

1. [export_cases.py](export_cases.py) reads the workbook and writes [data/cases.json](data/cases.json), preserving input types and the difference between an empty decision and an unspecified expectation.
2. [engine.py](engine.py) and [rules.sql](rules.sql) evaluate the same cases. [build_report.py](build_report.py) compares each implementation with the authored expectations and writes the [execution report](output/Tabby_Execution_Report.xlsx).
3. [mutation_check.py](mutation_check.py) records which cases catch selected mistakes in the Python rules in [mutation_results.csv](output/mutation_results.csv).

Edit the source workbook to change test cases. JSON and both files in `output/` are regenerated by the workflow. The boundary walkthrough is a formula-based illustration of one predicate. The authored expected outputs for the full decision are stored on Test Cases.

## Local results for the submitted workbook

Python and SQLite each matched all 74 defined expectations. The 14 exploratory cases await specification clarification. The cases detected all 25 selected changes to the Python reference rules. These results verify local reference implementations using synthetic inputs. Execution against Tabby's decision system requires its test interface.

### Mutation testing scope

Mutation testing changes the Python implementation only. SQLite is checked separately against the authored expectations for all 74 defined cases.

Eight of the selected mutations are detected by exactly one test case in this submission. For example, `average_500_inclusive` is detected by `R2-012`. That case is the only detector for the change from a strict to an inclusive repayment-average threshold among the current cases. See [mutation_results.csv](output/mutation_results.csv) for the detecting case IDs for every mutation.
